# 额度感知长任务

把目标组织成「分段执行 → 落盘交接 → 等待额度 → 恢复下一段」，直到达到本次明确的停止条件。交付实际计划、运行状态、交接文件和经核验的同聊天 heartbeat。仅创建本 skill 本身时，不为已结束的旧任务新建循环。

## 1. 开始前问清本次策略

先读取本任务已有指令，列出已明确的信息，只询问缺项；不把别的任务的用卡策略当成本次授权。使用可用的用户提问工具分组询问，等待关键答案。默认值是建议，不是用户已经提交的答案。

第一组必须明确：

- **目标与范围**：工作目录、最终产物、何种证据算完成；是否纳入后续新增项。已有描述时只补缺项。
- **停止条件**：做到任务完成，还是在指定日期/时区、最大轮次或额度保留下限时停止？多条件默认任一成立即停止。区分「本轮暂停，稍后续跑」和「整个任务终止，不再续跑」。持续监控必须有明确停止规则。
- **重置卡**：本次是否使用已有卡；是否希望过期前使用，还是仅额度耗尽时考虑？提供不使用、临期提醒后逐次确认、在工具允许范围内自动使用三种选择。选择使用时补问最多几张、允许/排除哪些卡、临期提前多久；说明提前重置会放弃尚未使用的窗口额度。询问意愿不等于已经兑换。

第二组补齐生成计划的信息：

- **额度阈值**：本轮暂停的五小时/周剩余阈值、恢复阈值和长步骤检查间隔。建议起点为五小时剩余低于 6% 暂停、恢复高于 95%，周保留 1%，每 30 分钟检查一次，长步骤约每 10 分钟及关键阶段边界检查。允许调整，并依据实际消耗增大预留。
- **交付与权限**：验收不可用/单项失败时继续其他项还是停止；待批准操作、Git 分支与提交/推送偏好、外部环境/素材条件。完成不自动包含发布、部署或迁移。
- **运行与通知**：固定机器能否保持开机、App 运行与网络可用；只在重要变化/完成/失败/需操作时通知，还是另有频率要求。默认同聊天、单写入者，不购买额度、切换付费来源、另建聊天或派生代理。

不要求回答无关问题。关键答案未到时可做只读调查和草拟计划；不能启用无人值守执行、兑换卡或把未回答的截止时间/卡策略写成同意。若需要等待，说明是用户要求的启动问询，并链接本 SKILL.md 本节。

## 2. 制作计划并核验能力

执行前读取 [运行协议](references/task-protocol.md)。按 [计划模板](assets/plan-template.md) 和 [交接模板](assets/handoff-template.md)，在工作目录建立独立运行目录，例如 `plans/long_runs/<task-id>/`；不得覆盖其他任务记录。

1. 创建 PLAN.md、state.json、HANDOFF.md、events.jsonl，列可单独交接的工作项和完成标准，区分已授权与待验收/待批准步骤。用户明确要求长期目标且有 goal 工具时才创建目标；否则以运行文件追踪。
2. 读取实际账号额度与卡详情；`usedPercent` 是已用，剩余是 `100 - usedPercent`，缺失/读取失败不是 0 或 100。额度账号共享，不固定推算还能跑几轮。记录观察时间，不以预计刷新时间替代实时检查。
3. 检索并读取现有 `get_usage_limits`、`automation_update` 等正式工具契约。复用对应现有自动化 ID；默认创建本聊天 heartbeat，初始 PAUSED。工具不可用时保留计划并明确人工续跑，不能用 cron 新聊天冒充同聊天续跑。
4. 核验线程绑定和状态转换，再暂停；实际定时触发、恢复执行、手机通知分别记录已验证/未验证。状态切换不证明全部通过，目标机器实际回调成功才记录续跑已验证。不为测试执行未授权业务。
5. 简短复述并保存已确认方案；授权足够时直接执行，不重复索要批准。用户只要计划时停在计划交付。关键策略变动记录实际来源，不隐式修改停止条件。

## 3. 单轮执行与提前交接

- 开工从 state.json、HANDOFF.md、日志及实际文件/Git diff 恢复，查其他执行者和未结束进程。暂停 heartbeat 并读回确认，再登记本轮持有者；重复唤醒不得启动第二个写入者。
- 每单元开始/完成、长单元安全阶段边界检查额度和停止条件。预计耗费会穿过预留时先拆段或交接，不能只等整包结束才检查。无法估计时先做可迅速落盘的小步，不能把未知耗费当零、直接开始不可拆的大操作。额度突降或读取失败，优先保存当前步骤。
- 检查点记录真实完成范围、原始错误、验证证据、文件/候选指纹、实际提交号、未提交差异、在跑进程、下一项和恢复命令。半成品保持 working/partial，失败保持失败，不为收尾改成 done。
- 中断、上下文压缩和 App 重启按同样交接处理。未完导出/外部变更先核对结果，避免重复执行；不一律杀不可中断进程或丢弃未提交文件。
- 达预留线进入 checkpointing，先写交接并保留成果；如要提交，预留提交与审批额度。审批失败记暂存/未提交差异，不丢成果。随后启用 heartbeat 并读回核验，标记 waiting_for_quota、释放持有者，结束本轮。
- 启用失败记录唤醒未落实并通知人工恢复。完成/截止优先于等待额度，任务结束时不重新启用 heartbeat。

用 `scripts/quota_decision.py --state STATE_JSON --usage USAGE_JSON` 验证暂停/恢复建议。它只读输入，不获取账号、控制自动化、执行任务或兑换卡；返回 action 不等于实际动作成功。

## 4. 等待、用卡与恢复

heartbeat 先检查完成/截止/人工暂停，再读实时额度和卡事件、查其他活跃回合。无变化或不满足恢复条件时安静结束，不重复报告；临期事件不能被「五小时未恢复」短路跳过。

- 满足本次恢复阈值、周额度可用且无活跃写入者时才暂停自身，恢复文件状态、登记新回合继续。预计恢复时间到达仍须读实时值。
- 任务已终止/完成、人工暂停或待关键答复时不自动恢复。截止后只做必要交接，不开新业务单元或消耗重置卡。
- 用卡意愿与工具权限分开：核对实际卡 ID、到期时间、数量、允许范围、工具资格与确认要求。要求每次明确确认时先询问本次兑换；启动选择自动不能覆盖工具限制，也不能换 CLI/App Server/UI 绕过。
- 原子落盘本次卡标识和 UUID idempotencyKey 再执行。不确定结果只用同一 key 重试；成功或 alreadyRedeemed 后重读额度和卡列表，不把延迟刷新当失败再兑另一张。
- 仅有数量、不能指定允许卡、临期但不满足兑换资格、额度/审批不可用时，如实报告限制并给人工恢复入口。不伪造兑换或制造消耗满足资格。不承诺硬限额后或设备离线时准时唤醒/兑换。

## 5. 终止与交付

重新对账范围与成果，输出逐项交付/验证/待验收总表。非完成停止条件写 stopped 并列剩余事项；只有完成标准实际满足才写 completed。暂停本任务所有自动化并核验，释放持有者，保存最终交接并通知；不留下空转任务。
