本轮每项的终点是“**待 Maya 验收的候选版本**”：保留原始行为和素材，整理可维护代码、必要的独立 API/界面适配、参数和影响说明、可运行的非 Maya 或 mock 回归检查，并给出真实 Maya 的直验步骤。未经过用户在真实 Maya 中验收的工具，仍留在 `tools_staging_pool/`；不得注册到 `maya_toolkit/tools/`、`ALL_TOOL_CLASSES` 或统一面板，不得在说明中写“已通过 Maya 实测”。用户以后逐项验收，再批量启动转正。这是用户对本轮工作顺序的明确要求；`AGENTS.md` 和 `DEVELOPMENT_SPEC.md` 的真实 Maya 验证门槛仍适用于转正。

`DEVELOPMENT_SPEC.md` v2.2 是框架接口的依据：`maya_toolkit.framework.base_tool.BaseMayaTool`、`validate(**kwargs)`、`execute(**kwargs)`、基类的 `run(dry_run=False, **kwargs)`、`parameters_schema`。部分分类 README 中的 `maya_toolkit.core.base_tool` 和 `get_schema()` 属于旧描述，不要照抄。候选适配可以放在原工具目录内，但不能提前注册为正式工具。对于无法合理套入 Maya 场景工具协议的独立程序、UE 工具或第三方套件，先提供清楚的边界和可调用适配方案，不做伪装性的继承。

## 2. 一次性准备：在工作机器上完成

1. 使用**同一个 Plus 账号**登录 ChatGPT 桌面版和手机端；在桌面版 Codex 打开此仓库的本地项目。先更新仓库，检查 `git status`，确认没有他人的未提交改动。不要用 Web 定时任务处理本机目录；本地定时任务要求工作机器保持开机、桌面版运行且项目路径可用。
2. 将该机器的 Codex 权限设为能写此仓库的 `workspace-write` 或等效范围。不要为了无人值守设成无范围限制的 full access。整理工作尽量只写仓库内文件；网络推送、系统目录写入或 Maya/UE 桌面交互如需额外权限，预先单独测试或留到有人时处理。定时任务可能以 `approval_policy = "never"` 运行，不能指望它在后台停住等手机授权。
3. 手机安装并登录 ChatGPT，启用 Remote/连接该主机，并打开相关推送或任务通知。**现场做一次两分钟后的测试提醒**：确认手机能收到通知、能打开这条项目聊天，并能看到/处理一次测试性问题。再在手机浏览器或可用的客户端实际找到 `Settings → Usage` 与可用重置卡界面；不要等到卡片到期才验证入口。
4. 保持工作机器不休眠，网络稳定，桌面版运行。先手动试跑下文的“首条指令”，查看第一次改动和通知，再创建每 15 分钟一次的同聊天续跑任务。只让**一条聊天/一个工作目录**写这批文件，防止多次任务互相覆盖。
5. 同步 `OBSIDIAN_SETUP.md` 所需环境。修改代码、待整理库或说明后运行 `scripts/sync_obsidian_knowledge.py`；`knowledge/_generated/` 只由脚本生成。

## 4. 文件进度与每项交付

首轮创建 `docs/staging_preparation/manifest.json` 和 `docs/staging_preparation/README.md`，从实时清单生成 57 项任务，检查目录和入口文件是否匹配；新增单元也要纳入。每项状态只使用 `pending`、`working`、`prepared_awaiting_maya`、`blocked`；没有真实 Maya 用户验收，不得标记 `accepted` 或 `promoted`。在清单中记录入口、原始文件 hash/提交、依赖、是否第三方、当前状态、所改文件、非 Maya 验证命令/结果、未验证点、对应的验收说明路径和最后更新时间。每次小批完成后原子更新清单，方便停机、限流、换聊天后恢复。

每项按下面顺序处理：

1. 阅读原脚本、素材、README、现有 `maya_toolkit.core` 和正式工具，记录可复用点、旧行为、Maya/Python/Qt/UE 依赖、场景与文件副作用。大型套件按“一个单元、多个子模块”细分工作，不因文件很多就直接标完成；保留第三方来源、许可文件和完整资源，不盲目重写供应商代码。
2. 在原工具单元目录内做可回溯改动或候选适配；优先修复明确缺陷、减少重复、分离 UI 与业务逻辑、补输入检查和外部写入保护。`validate`、`dry_run` 必须无场景和文件写入；场景写入的撤销范围、导出/覆盖不可撤销影响要如实说明。无 Maya 的环境不得通过导入原脚本来“试验”潜在的启动副作用。
3. 为该单元写 `docs/staging_preparation/<category>--<folder>.md`：用途、适用条件、入口/参数、前置依赖、输出、场景/文件影响、优化点、与 `core` 或其他工具的关系、非 Maya 验证证据、已知限制，以及用户在真实 Maya 中逐项验收的精简步骤和预期结果。涉及批处理、删除、杀毒、导出、引用替换的工具提供备份场景或临时目录的验收建议。
4. 运行与改动相关的轻量检查：静态解析/语法检查、隔离的逻辑单测或 mock、必要的纯 Python 回归。记录因 Maya/UE、Python 旧版本、插件或资产缺失而无法运行的检查。**这些检查不等同于真实 Maya 直验**。不得执行不可信的整包脚本、删除真实场景、批量修改用户素材。
5. 更新进度清单，运行 Obsidian 同步，检查 diff，按单元小提交。若遇到缺失资产、授权或行为无法判断，标记 `blocked`、写明具体原因，继续其他单元；若所有剩余项都依赖用户判断，则通过手机提问，不虚报全量完成。

全部完成的判据：实时清单中的每个单元均为 `prepared_awaiting_maya`，且各有代码或有理由的保留方案、验收说明、可复现的非 Maya 检查记录；总索引列出 57 项或启动后实际发现的数量，给出逐个 Maya 验收顺序。此时停止自动续跑并通知用户开始验收。用户验收后的批量转正属于下一阶段，届时再按 `DEVELOPMENT_SPEC.md` 迁移、注册、接面板并在 Maya 复测。

## 6. 不能保证的部分与应急动作

- 5 小时和周用量是共享且动态的；别的 Codex/Work 会话也会消耗它们。固定 5 小时刻度、每周期恰好 100%、在指定日之前耗尽整周额度都无法预先保证。实时 `resetsAt` 和实际限制反馈才是准绳。
- 本地定时任务受电脑开机、桌面版运行、网络、账号用量和权限影响；手机推送也取决于平台和设置。启动前完成一次通知与远程访问演练，并保留两个手机系统闹钟。
- 当前没有受支持的 agent 工具可以直接兑换银行中的重置卡。用户已同意手机端做两次确认；在确认之前，任务不能宣称“全程零人工”。如手机端不能打开 Usage，在到期前改用该机器的桌面版 `Settings → Usage` 或 CLI `/usage`。
- 如果限流导致 heartbeat 无法执行或权限要求使后台任务失败，到下一次计划运行仍可能不恢复。手机端查看 Scheduled/聊天状态；必要时手动点击 Run now 或在该聊天发送“按 manifest 继续”。
- 大型第三方套件及跨 Maya/UE 版本行为必须如实记录限制。完成候选版本不代表兼容性已在 Maya 通过。
